# 六条规则：AI 指令文件与记忆的治理方法

> **定位**：一份可以直接照抄的方法说明，讲怎么组织长期生效的 AI 指令文件（`AGENTS.md`、`CLAUDE.md`、系统提示词一类）以及随之膨胀的上下文记忆，面向使用 Claude Code、Codex 和各类 agent 工具的开发者。

## 这套东西解决什么

给 agent 用的指令文件天然只会变长：每踩一个坑，就想补一条；每确认一个事实，就想写进去。但下面几件事同时成立。

- 它每一轮都在占上下文，而且**过时的条目不会自己失效**，反而会压过当场实测的结果。
- 同一套规矩要在几个不同的工作区各用一份，手抄必然漂移。
- 有些规矩属于「人和模型之间的对话约定」，不是技术实现，社区里很少有人把它写成条文。
- 上下文超限时，工具通常不报错，只是**静默丢弃**一部分内容，而多数人不知道自己丢了哪一段。

这份文档只处理这四件事：**谁优先、怎么分层、一份源怎么同步到多处、超限时先丢谁**。它不让模型变得更聪明，只规定文件和对话怎么用。每条都附了可直接抄进文件的文本，判据尽量写成「能一眼判真假」的形式。

（文中工作区一律用编号指代：工作区 A（干活区）、工作区 B（内容向）、工作区 C（娱乐向）、工作区 D（娱乐向）。）

---

## 一 · 现实优先

**问题**：指令文件以「指令」的身份进入上下文，工具输出以「工具结果」的身份进入。模型在训练中被调成对前者的权重更高，于是陈旧的记忆不是默默失效，而是主动覆盖现实。

**证据**（arXiv:2610.30571，320 次运行）：给模型一份与现有代码相矛盾的规则文件，不加任何说明时，两个被测代理合计在 **90.1%** 的情况下会跟着陈旧文件走。更值得注意的是第二层现象——**Claude Code（代码代理）**在 80 次里 **79 次明确指出这处冲突**，然后照样按文件执行；**Codex CLI（命令行代码代理）**则在 80 次里有 **20 次**把原本正确的代码改写成符合陈旧文件，其中 17 次项目测试当场失败。而只加一句「以现有代码为准」，跟随现实的比例从 **4.2% → 91.4%**，测试通过率从 **89.4% → 100%**。

**落地文本**（可直接抄）：

```markdown
> 本文件里任何结论，与当场实测的文件内容 / 命令输出冲突时，一律以实测为准；
> 发现冲突要讲出来，并顺手修正本文件里对应的那一条 —— 不要照着本文件执行。
```

**要点**：这句话的成本是一行，收益是把「照旧执行」换成「先看现场」。它要写在靠前的位置，并明确要求「顺手改文件」——只写「以实测为准」，冲突会被指出来，但不会被修掉，下一轮又回到原点。

## 二 · 问一次不等于问过

**问题**：AI 提问时常常顺手给一个默认值，然后继续干活。提问方以为自己已经问过了，回答方并不认为存在一个待答的问题——**问题就这样静默消失**。这件事的坑在于双方都没做错什么：一方给了默认值，一方保持沉默，两边都以为对方接到了。

**判据**：一条问题只要没有明确答复，它就一直挂在台面上。沉默既不是同意，也不是它自己消失了。

**落地文本**：

```markdown
> 要人做决定时：写清「不回答会怎样」；在拿到明确答复前，每一轮都要把这条未决项重提一次，
> 直到对方答复或明确作废。不许问一遍就沉默、事后当默认过。
```

**为什么单列一条**：这不是技术点，是人和模型之间的对话契约。它来自一次真实事故——AI 提出「某两个工作区缺少某条规矩，要不要补」，附了默认值就继续干活，问题一直沉到被人自己翻出来。

同一条对不同形态的对话都成立：AI 对 AI、派发任务给子代理、写在文档里留给下一个读者的待办项——**凡是需要对方回一句话才能推进的地方，都要把「不回会怎样」写出来**。

## 三 · 按「可推断性」分层，而不是按「重要性」分层

按重要性分层是个直觉陷阱：所有规矩看起来都重要，最后哪一条都下不去。可执行的是另一个判据：

> **模型推不出来、也现查不到的 → 留在常驻层；能现查的 → 下沉成按需加载。**

| 内容类型 | 例子 | 放哪 |
|---|---|---|
| 踩过的坑、禁令、判定顺序、症状→处置表 | 「别把『读不到』当成『不存在』」 | 常驻层 |
| 可现查的清单 | 盘符表、版本号、路径清单、脚本正文 | 按需加载 |
| 多步流程 | 装插件的步骤、体检怎么跑 | 按需加载 |

**为什么**：常驻层每一条都在付上下文成本，而且必然过时。一项针对上下文文件的实证研究（`arXiv:2602.11988`，ETH Zurich；**下引正文基于 2026-09 修订版 v3**）显示，提供上下文文件**并不会普遍地提升任务成功率，反而平均使推理成本上升 20% 以上**；这一点在不同 LLM、不同编码 agent、以及「LLM 生成」与「开发者手写」两类文件上都成立。**摘要的结论是一组对照**——指令被执行得很好，但被推荐的仓库概览没有帮助（"instructions … are well followed … repository overviews … are not helpful"）；**论文正文（§4.3、附录 A.2、§6）进一步给出机制**：因为文件里的指令会被认真执行，模型于是**多跑测试、多读文件、多做检查**，这些动作对完成手上那个具体任务而言全是不必要的。**论文正文还解释了「仓库概览为什么没用」**：不是概览本身没价值，而是它与仓库里已有的 README、`docs/` 冗余——附录 B 在手动删掉全部文档、让上下文文件成为**唯一**文档来源的情况下，LLM 生成的上下文文件反而**平均提升 2.7%**（该实验排除了 Claude Code）；至于成本从哪来，§4.3 给了一个**尚未证实的猜测**：这些额外指令让任务本身变得更难。不过这篇论文的结论**并不是「别写指令文件」**——它的结论是：上下文文件对声明非标准编码约定是有用的，任何想靠它提升性能的做法，部署前都必须严格验证。

**水位参考**：主流平台对单个指令文件的篇幅都有明确的上限建议。**我们自己的实测**：常驻层从 44 KB 压到 34 KB 之后，全部判定规则一条没删。

## 四 · 一份源 → 多处注入 + 自检防漂移

**问题**：同一套规矩抄进多个工作区，必然漂移。实测过这种情况：一个工作区停在旧版本，另一个没跟上当天的整合，两边都以为自己是最新的，谁也不会主动去对。

**做法**：

```
rules-source.md（唯一源）
   └─ 同步脚本 ──→ 工作区 A 的标记区块
              └→ 工作区 B 的同一区块
   └─ 同步脚本 --check ──→ 只检查不写，漂移时退出码非 0（可挂 CI）
```

要点有两个：可同步的区块用一对显式标记围起来（避免整文件覆盖掉工作区自己的内容）；同步脚本必须带「只检查、不写入」的模式，否则它只能靠人想起来跑。

配套一个自检脚本，一次报出三件事：运行状态、文档与实现是否一致、各区块是否与源一致。

**可迁移性**：任何「同一份文本要注入多处」的系统都适用——多仓库、多个 agent 工具、同一套规则的多语言版本。它不解决内容本身写得好不好，只保证多处看到的是同一份。

## 五 · 分区原则：别把「统一」当「规范」

| 区类型 | 处理 |
|---|---|
| **干活区**（要出交付物的） | 顶真：全套规矩、事实以实测为准、清单下沉到按需加载 |
| **娱乐区**（出内容、玩创作为主） | **放开发散**：只保底两条——事实以实测为准、问决定要写清后果；不加交付纪律，不强制瘦身 |

**为什么**：社区默认「一份指令文件通吃所有场景」，结果是把娱乐区灌满工程纪律，创作被压住。我们实测过这个错误——给两个娱乐区接上完整规矩之后，其中一个工作区的注入预算直接冲到 92%；而同期的实际产出是：**好点子恰恰是在那两个「没人管」的区里长出来的**。

**一句话**：轻的地方出点子，重的地方固化点子；别把轻的地方也搞重。

## 六 · 常驻层要有预算自知（超限时谁先被丢）

多数人不知道自己指令超预算时会发生什么，工具多半也不报错——它只是悄悄少给你一部分。我们的做法是把降级顺序写进文档，让「丢了谁」从猜测变成可查的事实：

```
整条链超预算 → ① 最宽泛的那层（全局广播层）被整份丢弃
              → ② 仍放不下 → 对工作区层从尾部二分截断
              → ③ 开头留一行提示：哪一层被省略、哪一段被截断
```

由此推出两条操作纪律：

- **最要紧的规矩放工作区层**——它活得最久，只在最后一档才会被截；
- **新规则不要加在文件末尾**——尾部最先被截。

**边界**：这个顺序是读实现源码得出的，各家工具的机制不同，换平台必须重新确认自己的降级顺序。但「先搞清楚超了会丢谁」这个动作本身可以照搬。

## 我们相对社区的位置（诚实版）

**在外面（有证据支撑）**

1. 「问一次不等于问过」——检索下来没有找到把它写成对话契约的公开文本。
2. 「现实优先」——支撑它的论文刚发表不久，也尚未见到现成模板把它作为默认条款内置。
3. 「用可推断性做分层判据」与「知道超预算先丢谁」——后半段是读实现源码挖出来的，社区讨论里少见。

**在里面（别吹）**

- 分层指令文件、CI 防漂移、三层记忆、规则 lint，都是社区标配；
- 这类检查已有免费工具在做，平台方同样在把它内置。

**三个「在外面」的共同形状**：它们都不提升模型能力，只规定**人和模型之间的约定**。而社区的精力几乎全花在前者上——这也正是这份文档值得单独存在的原因，也是它不值得被当成新技术的原因。
